## telegram-bot-files-groups

- **CONFIRMED**: Cloud Bot API getFile can download only files up to 20 MB, and the download link is valid for at least 1 hour. getFile may not preserve the file name or MIME type.
  - Evidence: Fresh api.json (Bot API 10.3, Aug 24 2026) methods.getFile quotes all three statements; bots/faq snapshot line 90 says 'only work with files of up to 20 MB'. A fresh clone of tdlib/telegram-bot-api (e3e9dd8e) has Client.h:72 MAX_DOWNLOAD_FILE_SIZE = 20<<20 (20 MiB). Client.cpp:17041-17044 returns 400 'file is too big' and :9378-9383 cancels downloads past the limit. The server also sets the TDLib option ignore_file_names (Client.cpp:9405-9407).
- **CONFIRMED**: User upload limit is upload_max_fileparts × 512 KB. The mandatory defaults are 4000 parts without Premium (2,097,152,000 bytes ≈ 2000 MiB) and 8000 parts with Premium (≈ 4000 MiB).
  - Evidence: api/files snapshot lines 33-40; api/config line 87 ('full list of defaults that must be used'), lines 496-497 (4000/8000) and 666-669 ('multiply by 524288'). 4000×524288 is exactly 2000 MiB. tdlib/td@bc9c263 PartsManager.h:56-59 hard-codes 4000/8000 and 512<<10; FileLoaderUtils.cpp:274 and FileManager.cpp:52 cap at 4000 MiB. Nuance: these are fallback defaults used only when help.getAppConfig lacks the key (api/config lines 85-86), not hard 'mandatory' limits. TDLib ignores the live config value.
- **CONFIRMED**: The local Bot API server needs --api-id and --api-hash in every mode. --local adds unlimited downloads, 2000 MB uploads, file:// uploads, HTTP/any-port webhooks, max_webhook_connections up to 100000, and an absolute file_path.
  - Evidence: README lines 50-62 (fresh clone) are verbatim. telegram-bot-api.cpp:304-309 checks api-id/hash unconditionally, and :212-222 defines the options and env defaults. Each feature is gated by local_mode_: Client.cpp:10781-10786 (file:/), WebhookActor.cpp:704-715 (HTTPS and ports) and :776-787 (IP), Client.cpp:17216 (100000), :9378 and :17041 (size), :17960-17965 (absolute path). The 2000 MB upload figure is not a server constant; it is Telegram's non-Premium MTProto part limit.
- **CONFIRMED**: In local mode file_path is the absolute path on the Bot API server's filesystem; the server routes only /bot<token>/... and does not serve file downloads, so the bot must share a filesystem/volume or run its own file server.
  - Evidence: Client.cpp:17959-17971 emits file->local_->path_ when local_mode_. HttpConnection.cpp:29-35 rejects anything not starting with '/bot' with 404. The same lack of a /file route applies to non-local self-hosting.
- **CONFIRMED**: Privacy mode on by default except bots added as admins; admins receive all messages; privacy-on bots get only /cmd@bot, general commands if last bot, via-bot messages and replies; all bots get service messages; /setprivacy change needs re-adding.
  - Evidence: Fresh telegram-crawler snapshot: bots/features lines 433-444 and bots/faq lines 48-58 verbatim, including '(the bot will need to be re-added to the group for this change to take effect)'. The FAQ adds 'except messages sent by other bots'; the Bot-to-Bot mode exception is at bots/features lines 290-301.
- **DOWNGRADE**: The Bot API has no method for reading group chat history, and pending updates are kept for at most 24 hours. Uploads made before the bot joined, or during more than 24 h of downtime, cannot be collected.
  - Evidence: No history method among the 185 api.json methods; bots/api line 172 states 24 h; Client.cpp:18474 has left_time = message_date + 86400 - now. But the 'cannot be collected' conclusion is overstated. When a member replies to an old upload, the server fetches the replied-to message via getRepliedMessage (Client.cpp:19371-19376, 8673-8691) and delivers it as reply_to_message with the document and its file_id. forwardMessage, copyMessage and forwardMessages accept arbitrary message ids in groups and member supergroups (Client.cpp:9057-9081, 9084-9103, 14440-14454). Whether Telegram returns pre-join messages is undocumented.
- **CONFIRMED**: getChatMember is only guaranteed for other users if the bot is admin; the server requires ReadMembers for other users; a non-member bot in a private supergroup gets 403 'bot is not a member of the supergroup chat'.
  - Evidence: api.json getChatMember text verbatim; Client.cpp:16323-16336 (ReadMembers when user_id != my_id_); Client.cpp:8839-8857 (403 not a member / kicked). Clarification: ReadMembers is an internal access level, not an admin check. For supergroups it equals Read; for basic groups it only requires an active group with the bot neither left nor kicked (Client.cpp:8814-8837). Non-admin failures come from Telegram's servers.
- **CONFIRMED**: ChatMember status strings are creator, administrator, member, restricted, left and kicked; restricted exists only in supergroups and carries is_member, permissions (incl. can_send_documents) and until_date.
  - Evidence: api.json ChatMemberOwner/Restricted/Member/Left/Banned fields; get_chat_member_status mapping in Client.cpp; JsonChatMember emits is_member, permissions and until_date only when chat_type_ == Supergroup; TDLib DialogParticipantManager.cpp:2508-2510 'Can't restrict users in basic group chats'.

Additional findings by the verifier:

- Cloud (non --local) webhooks: HTTPS only, ports 443/80/88/8443 only, IPv4 only, no reserved IPs (VERIFIED WebhookActor.cpp:704-715, 776-787; bots/api line 329). --local lifts all of these.
- In --local mode the absolute file_path contains the full bot token: the per-bot directory is <dir|files-dir>/<bot_token>[/test]/ with ':' replaced by '~' unless --allow-colon-in-filenames (VERIFIED Client.cpp:8603-8612). Never log or expose file_path to Mini App clients.
- In --local mode getFile answers only after the whole file has downloaded to the Bot API server's disk (VERIFIED Client.cpp:17045-17048 and on_update_file 9373-9386, which waits for is_downloading_completed_). A 1-2 GB ROM blocks getFile for the full transfer, so use long timeouts and async handling, and plan disk cleanup under --dir.
- Old uploads can be harvested via the reply route: when a member replies to an old document with /cmd@bot, the server fetches the replied message (getRepliedMessage, Client.cpp:19371-19376) and delivers reply_to_message with the document's file_id. It may fail under privacy mode (log text at Client.cpp:8680-8682). forwardMessage/copyMessage/forwardMessages (≤100 ids) accept arbitrary ids in groups and member supergroups (Client.cpp:9057-9103, 14440-14454); whether pre-join messages are returned is untested.
- Basic groups: admin is boolean and owner-only at the MTProto level (TDLib DialogParticipantManager.cpp:572 messages.editChatAdmin; :2542 'Need owner rights in the group chat'). Telegram Android migrates a basic group to a supergroup when non-default admin rights are chosen (ChatRightsEditActivity.java:1536-1544), but its isDefaultAdminRights() (1105-1108) counts 'all listed rights false' (manage_chat only) as default. A manage_chat-only startgroup link on a basic group may therefore yield a full basic-group admin without migration (ASSUMED; test on each client). Plan for the chat_id change on migration.
- Telegram Games are a group-capable alternative launch path: sendGame works in groups (only channels and channel DM chats are excluded, per api.json); a callback_game press gives the bot from.id and message.chat.id, and answerCallbackQuery.url opens the game URL (VERIFIED, api.json). The bot can embed a server-signed (chat_id,user_id) token and so bind the chat id that direct-link Mini Apps lack. Games do not get Mini App initData (ASSUMED). Non-game callbacks may answer with t.me links, so a per-user ?startapp=<signed token> is a possible chat-binding route (ASSUMED; test).
- Doc inconsistency: the WebAppInitData table says start_param is the startattach value for attachment-menu launches only, while the direct-link sections (bots/webapps lines 180, 200) say startapp is passed in start_param and tgWebAppStartParam.
- tdlib/telegram-bot-api is Boost Software License 1.0 (README line 98, LICENSE_1_0.txt): permissive, self-hosting is fine.
- TDLib hard-codes the 4000/8000 part limits (PartsManager.h:56-59) and does not read the live upload_max_fileparts_* config.

## webview-capabilities

- **CONFIRMED**: The Gamepad permissions-policy default allowlist is '*' in Chromium, WebKit and Gecko, so a cross-origin Mini App iframe in Telegram Web does not need allow="gamepad". Web K and Web A Mini App iframes do not include it.
  - Evidence: Re-fetched every file. - Chromium main permissions_policy_features.json5:361-364: Gamepad feature_default EnableForAll. The global default is EnableForSelf (:32-33). - WebKit PermissionsPolicy.cpp:227-233: Gamepad maps to "*". - Gecko PermissionsPolicyUtils.cpp:43: {"gamepad", eAll}. - Fresh tweb master webApp.tsx:1063 allow has no gamepad. telegram-tt master iframe.ts:13 IFRAME_ALLOW_ATTRIBUTES (used at WebAppTab.tsx:1246) has no gamepad. - Chromium navigator_gamepad.cc:108-112 only enforces the policy. A cross-origin subframe is only use-counted (:138-141); there is no focus requirement. - Not checkable from here: a Permissions-Policy response header on web.telegram.org.
- **CONFIRMED**: In WKWebView (iOS), gamepad input goes only to the page whose WKContentView is first responder of the key window, and a single tap on web content makes it first responder.
  - Evidence: - WebKit main UIGamepadProviderIOS.mm:38-53 returns the page of [[UIApplication sharedApplication] keyWindow].firstResponder when it is a WKContentView. Additional findings by the verifier:

- VERIFIED (WebKit main XPCServiceEntryPoint.mm:208-220; UnifiedWebPreferences.yaml disableInLockdownMode): Apple Lockdown Mode sets JSC useWasm = false and disables the JIT, WebAudio, Gamepads, IndexedDB, CacheAPI, WebRTC, WebTransport, WebCodecs and WebGL. Architecture (b) cannot run there at all, and (a) loses WebRTC and WebCodecs too. Detect Wasm and show a clear message. REPORTED: WebKit bug 273824 says Wasm stays blocked even when the app is excluded from Lockdown Mode (iOS 17.4+).
- VERIFIED (client/src/api.ts:88-130 plus the project catalogs): every viewer in (b) downloads the ROM and BIOS (CPS2 25-46 MB raw, Neo-Geo up to about 93 MB) plus about 3.1 MB of gzipped core. This adds first-join delay and bandwidth, and puts a ROM copy on every device. The report's bandwidth section (§6) leaves it out.
- ASSUMED (derived from the report's own §7 netcode v2): in a server-deadline rollback design, rollback depth depends on each player's own RTT (R_i ≈ (RTT_i + jitter)/T - D), not on the average. A player at 140 ms RTT needs about 8-9 frames, which reaches the GGPO 8-frame window. The low-RTT player rolls back very little.
- VERIFIED (libwebrtc network_types.h:251, pacing_controller.h:84-114, pacing_controller.cc:366-375): the pacer's default 40 ms burst window (63 KB cap) means small P-frames are usually not delayed by pacing. Keyframes and large frames are the latency risk, so use intra-refresh.
- VERIFIED (video_receive_stream2.cc:1239-1242, 1272-1281): with playout-delay max 0, the frame max overrides the A/V-sync minimum, so streamed video runs ahead of audio and audio arrives later (NetEq). With min 0 and max > 0, libwebrtc also sets max_composition_delay_in_frames for Chromium's low-latency renderer (Chromium side ASSUMED). Test 0/0 against 0/X. Lockstep has no network audio path.
- REPORTED (GameStar via gamepressure): GeForce NOW Competitive mode (720p120, V-Sync off) adds only about +27-30 ms over local, the best commercial streaming data point. Stadia on a TV at 4K was as bad as +216 ms (PC Gamer).
- VERIFIED (FBNeo cps.cpp:2232-2235, 2245, 2248-2251): CPS1/CPS2 run at 59.63 Hz with a 384-wide screen and a 68000 at 11.8 MHz (CPS2). Replicas must be paced to the server frame clock, not to rAF.
- VERIFIED (BCD 8.1.5): relaxed SIMD ships in Chrome, Edge and Android WebView 114+ and in Firefox 146+, so a relaxed-SIMD build would diverge across CPUs and engines. Never pass -mrelaxed-simd. The project's build-cores.sh has no SIMD or pthread flags.
- VERIFIED (libwebrtc rtp_video_stream_receiver2.cc:306-307, 371-372, 796-803): a receiver-side field trial, WebRTC-ForcePlayoutDelay, can override the playout-delay extension. Page JS cannot reach it, so in Telegram webviews the server must still send the extension.
